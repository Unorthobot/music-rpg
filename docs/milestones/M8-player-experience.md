# M8 — The player experience

**Baseline:** tag `m8-headless` (commit `8460dfd`). The challenge, the lifecycle,
the three judges, the consequences and the whole causal record exist and are
proven. Nothing here requires a new judging capability; where the build needs a
capability that exists but has never been called from the running game, it says so
explicitly and first.

This is the UX acceptance specification. It is not a wishlist.

## The principle

> **A battle is a night you agreed to, not a fight you clicked.**

The player's part is entirely over before anybody performs. They decide whether to
accept, what they can find out, what angle to take, and how much of their career
to spend preparing. Then game time reaches the night, and they find out what three
people made of it.

Two constraints follow, and both are inherited rather than invented.

**The world creates, the screens reveal.** No interface in this specification may
create a challenge, bring a night forward, judge a round, or apply a consequence.

**Facts before prose.** The judges established what happened. Every word this
milestone puts on a screen is a *reading* of a decomposition that already exists
in the row. No sentence may decide anything, and no sentence may say something the
decomposition does not support.

## The journey

```
challenge arrives
  → player becomes aware              (Messages, Notifications)
  → accept or decline                 (both complete answers)
  → scout                             (reduce uncertainty; never remove it)
  → choose strategy                   (intent, declared before preparation)
  → prepare                           (days and money a record could have had)
  → the night arrives through game time
  → the battle resolves as a world fact
  → the player reads the judges' decision
  → World, Career and the relationship reflect the aftermath
```

**No battle result may be generated by opening the battle route.**

## Four surfaces, four questions

`/battles/[id]` earns a dedicated route because a battle is a multi-step,
time-bound confrontation with its own lifecycle — challenge, scout, strategy,
prepare, event, decision, aftermath. It is a **situational surface**: it exists
while a confrontation does, and it is not a section of the game.

**No global navigation item.** Awareness arrives through Messages and the
Calendar, both of which already exist and already carry badges.

| Surface | The question it answers |
|---|---|
| **`/battles/[id]`** | What am I doing about this confrontation? |
| **Messages** | Who wants something from me? |
| **Calendar** | When does it happen? |
| **World / Career** | What became true because it happened? |

That separation is load-bearing and must be preserved. In particular the battle
route does not become a second home for messages from the challenger, and the
Calendar does not grow battle-specific controls.

## Resolution is a scheduled world event

`resolveBattle` exists, is proven, and **has exactly one caller: the test suite.**
A career can currently accept a battle, declare an angle, prepare, watch the night
arrive on the Calendar, and then nothing happens forever. That is the correct
state for a headless milestone and an unshippable one here.

The fix is not "call it at step 4.5". The causal idea is what matters, and it is
one the game will need again:

```
time advances
  → due scheduled world events resolve
  → downstream projections, relationships and opportunities react to what is now true
  → surfaces reveal the new facts
```

A battle is simply **the first scheduled world event that needs this treatment**.
Releases tick because they are already in flight; sessions wait to be opened;
offers expire by sweep. A battle is the first thing that *happens on a date
whether or not anybody is looking*.

**Requirement:** implement the smallest battle-specific orchestration that
preserves that seam. A battle whose `scheduled_game_time` the world has reached
resolves during the day advance, before the systems that should be allowed to
react to it. **Do not build a generic event scheduler in this milestone.** The
architecture does not yet demonstrate the need for one, and inventing a registry
for a single event type would be the wrong milestone's work — but the ordering and
the naming should be such that a second scheduled event type slots in beside the
first rather than replacing it.

**The rule that outranks all of the above:** the battle result exists because game
time reached the event. Never because the player opened `/battles/[id]`. A player
who never opens the route still has the battle happen, is still notified, and
finds the decision waiting when they arrive.

## The player/internal boundary

Everything in the left column exists in the data and **must never reach a player**.
World Control may expose all of it and already does.

| Internal | Player-facing |
|---|---|
| The seven performance facts (`writing = 47.955`, …) | *nothing* — never a number, bar, star, or chart |
| `derivation[].base / strategyShift / preparationShift / composureShift` | *nothing* |
| `challengerTotal`, `opponentTotal` | *nothing* |
| `JudgeContribution.weight`, `.contribution`, `.term` | *nothing* |
| `margin` | *nothing* — not even as "close"; the decision already says it |
| `strategyAptitude` | *nothing*, and nothing from which it can be inferred |
| `artist_skills.*`, `artist_psychology.*` | *nothing* |
| `roomComposition()` shares, cohort slugs, `attention`, `qualities` | *nothing* |
| `BattleStandingPressure.fame / respect / heat` | *nothing* — see *Consequences* below |
| `relationships.rivalry` as a number | *nothing* — see *Consequences* below |
| `battles.consequences` (the whole JSON) | *nothing*; no player surface reads this column |
| `scouting.findings[].observed` (raw values) | *nothing* — the describer reads it, the screen does not |
| `seed`, `simulator_version`, `engine_version` | *nothing* |
| eligibility rules, `ranking.score`, `rank`, `suppressedBy` | *nothing* (M7's boundary, unchanged) |
| `decision = "2-1"` | **shown**, as three perspectives and a formatted "2–1" |
| `TECHNICAL / STRATEGIC / AUDIENCE` | "The writing", "The plan", "The room" |

**The single hardest rule, stated plainly:** a performance fact is never rendered
as a quantity in any form. Not a number, not a bar, not a five-star rating, not a
hexagon. The moment a player can see that their writing was a 48, the game has
stopped being about what happened in a room and started being about a stat screen,
and every subsequent decision becomes optimisation.

## The chain, surface by surface

### 1. Somebody calls you out

Arrives as a message from a named artist, in their voice. **This already works**
and needs no new capability — `battleChallengeMessage` is wired through
`communicateOpportunities`.

The challenge appears in Home's "On the table" alongside any promoter nights, and
**must not be visually distinguished as more important**. The director already
ranks challenges below paid work early in a career; the interface must not
contradict that by making the battle louder than the booking.

### 2. Accept or decline

Both are complete answers. See *Declining* below — getting it wrong is the most
likely way this milestone fails.

Accepting books the night on the Calendar and opens `/battles/[id]`.

### 3. Scout — sourced, incomplete knowledge

**Scouting reduces uncertainty. It does not reveal the opponent model.**

It must never render as a character sheet. This shape is forbidden:

```
Writing:            Strong          ✗
Crowd work:         Exceptional     ✗
Strategy tendency:  WIN_THE_CROWD   ✗
```

That is the internal model in adjectives. Every insight must instead be
**attributed to the provenance the system actually owns**, translated into the
player's language:

| `ScoutingFinding.source` | Player-facing heading |
|---|---|
| `WORLD` | What you've heard |
| `SCENE` | Around the scene |
| `RELATIONSHIP` | What's already between you |
| `BATTLE_HISTORY` | From previous battles |

```
Around the scene
KGOSI carries a room in Braamfontein. People turn up for the night as
much as for whoever's on it.

From previous battles
He's been in rooms like this before and come out of them fine.

What you don't know
What he's actually preparing for you.
```

**Decision: no named advisor in M8.** An insight attributed to a specific person
— *"LEX: don't get dragged into trying to out-perform him"* — reads better and is
not backed by anything. `scoutOpponent` takes no crew input, and the model has no
concept of a crew member holding an opinion about a battle. A named advisor
requires a real crew-advice and knowledge system, which is **out of scope for this
milestone**. Every heading above corresponds to a `source` the headless model
already sets; nothing here invents a voice the world does not have.

**Requirement:** *What you don't know* is a first-class section, not a footnote,
and maps to the real `unknowns` array the headless model already produces —
including *"What they will actually come with — nobody declares an angle in
advance, and guessing would not be scouting."* That sentence is the entire design
of the strategy decision: **the player chooses an angle without knowing the
opponent's.**

Scouting must never expose, or let anybody infer:

- `artist_skills` or `artist_psychology` values, in numbers or adjectives keyed
  one-to-one to them;
- `strategyAptitude`;
- any prediction of a performance fact;
- judge weights or what any judge will value;
- the opponent's actual declared strategy.

Scouting has no mechanical benefit and the interface must not imply one. It costs
nothing and must not be framed as an advantage purchased.

### 4. Choose the angle — intent, not modifiers

Three options, each presented as artistic and competitive intent:

| | Copy |
|---|---|
| `OUTWRITE` | **Outwrite them** — Make the writing impossible to ignore. Let the room catch up. |
| `WIN_THE_CROWD` | **Win the crowd** — Don't give them the room. Make them yours first. |
| `TAKE_THEM_APART` | **Take them apart** — Listen for openings. Answer what they actually bring. |

Never shown: `+writing`, `−crowd work`, aptitude percentages, performance bonuses,
or numerical trade-offs of any kind.

One consequence statement is appropriate and sufficient:

> You can't change your approach once preparation starts.

**On pronouns.** The copy above says *them* deliberately, and that is the
milestone's answer rather than a placeholder. The world states pronouns for two of
the three rivals in biography prose and for KGOSI not at all, and there is no
structured pronoun field anywhere in the codebase. **The interface must not infer
an opponent's pronouns from their name.**

**Decision: no pronoun field in M8.** Templating on the name ("Outwrite KGOSI") or
using *them* covers every surface this milestone builds, and expanding the
character schema to support gendered copy would be a content-model change made for
a wording preference. Structured character pronouns are recorded as future
content-model debt; they are not a prerequisite for anything here.

### 5. Prepare

Up to three sessions. Each costs money through the ledger and one game day booked
as `REHEARSAL`.

**Requirement:** the cost is shown as what it actually is — *days a record could
have had*. The model's whole justification for preparation is that entering a
battle becomes a decision about the career rather than only about the battle, and
an interface showing only a fee has hidden the real price.

**Requirement:** preparation is never presented as improving the odds by a stated
amount. It sharpens what the artist can already do; it does not hand them ability.
The honest copy is about work, not about probability.

### 6. The night

Resolves on the day advance, because game time reached it. The player is notified.

### 7. The judges' decision

The most important screen in the milestone, and **not a scorecard**. That word is
banned from the codebase and the copy: it invites a numeric optimisation mindset
about a thing that has no numbers.

The shape foregrounds the three perspectives and what each of them decided:

```
KGOSI TAKES IT
2–1

THE WRITING          KGOSI
His rebuttals landed cleaner and his structure held together.

THE PLAN             YOU
You committed to your angle and carried it through better.

THE ROOM             KGOSI
He understood what this crowd wanted and gave it to them.
```

**Requirements:**

- **Three perspectives, stacked vertically on mobile.** Never side-by-side cards,
  never a table, never a compressed comparison row. The stack is the layout at
  every width; on desktop it may breathe, not rearrange.
- **The dissent must be legible as a dissent.** A 2-1 in which the player carried
  one perspective is a materially different night from a 3-0, and the screen has
  to make somebody feel they were not simply beaten.
- **Each line is generated deterministically** from that judge's own
  decomposition — the largest one or two contribution differentials and their
  recorded `note` — by a describer that lives beside `opportunities/describe.ts`
  and follows the same rule: same facts, same words, every time, and nothing that
  can change an outcome. **No model writes a battle line.**
- **"2–1" is formatted for display.** The `decision` column holds `"2-1"`; the
  en dash is presentation.
- **The player's own round is described in the same register** — what they went
  for and how it landed — and never enumerated. A list of seven labelled values is
  a stat screen whatever the labels say.

### 8. The aftermath — consequences through the world

**There is no battle-reward screen, and there are no reward numbers.**

Forbidden, as figures:

```
Respect +0.45    Heat +0.90    Fame +0.0792    Rivalry +20     ✗
```

Equally forbidden, as gamified copy — the same idea with the number hidden:

```
Respect increased!    Heat increased!    Rivalry increased!    ✗
```

Both treat a night in a room as a payout. Instead the aftermath is **experienced
through the surfaces that already own it**, in the world's own terms:

> People noticed how close you made it.
>
> The room is still talking about it.
>
> Whatever this was between you and KGOSI, it isn't over.

And then, without announcement:

- standing changes, and **Home and Career show it where they already show it**;
- the relationship surface reflects the rivalry, in M6's existing words;
- World carries the public fact, because a resolved battle is `LOCAL_PUBLIC`;
- Career remembers it as history.

**Requirement:** no player surface reads `battles.consequences`. The aftermath
lines are read from the judged result and the recorded interactions; the standing
movement is observed where standing lives.

## Declining is a valid career identity

The model is unambiguous: `CHALLENGE_DECLINED` moves familiarity and tension and
**cannot move respect in either direction**. The interface is where that gets
honoured or quietly reversed.

- **No warning copy.** No "are you sure?", no "this may affect your reputation",
  no consequence preview. There is no consequence to preview.
- **No cowardice language**, in copy, iconography or tone.
- **No visual weighting.** Accept and decline are two answers, presented as two
  answers.
- **No nudges.** Nothing anywhere suggests the player should accept.
- **No streaks, counters, participation meters or completion state.** Nothing
  counts battles fought, declined or won.
- **No re-prompting.** A declined challenge is answered; the rival's reply lands
  in Messages and the thread closes.
- **Career remembers it neutrally**, in the same register as a declined booking.

The acceptance test is blunt: **a player who declines every challenge for an
entire career must never be shown anything implying they are playing the game
incorrectly.** An artist who does not battle is an artist who does not battle.

## Copy discipline

- Never "scorecard", "score", "points", "rating", "stats", "metrics".
- Never "opponent" as a noun for a person who has a name.
- Never "match", "bout", "round X of Y", "VS", or belt/rank vocabulary.
- Never a percentage or probability on any battle surface.
- The judges are "the writing", "the plan", "the room".
- A loss is a loss. No consolation framing and no "you'll get them next time" —
  the game does not know that and should not say it.

## Out of scope

- **Any live or animated battle sequence.** The round is a fact to read
  afterwards, not a scene to watch. Animating it implies the player influences it
  while it happens, which is false.
- **Generated bars, lyrics or audio, in any surface.**
- **Rankings, leagues, belts, streaks, battle records.**
- **A rematch button.** The director may legitimately produce a second challenge —
  rivalry now feeds its ranking — and it arrives the way the first did. A
  "challenge them back" control would make a screen create a world fact.
- **Player-issued challenges.** `player_side` exists so the model can express one;
  the interface is a different question about who a player may approach.
- **PvP, tournaments, community voting.**
- **A generic world-event scheduler.** See *Resolution* above.
- **Changing simulation coefficients, the headless model, or the golden scenario.**

## Acceptance criteria

### Behaviour

1. **No screen creates, schedules, judges or resolves anything.** Opening every
   battle surface repeatedly, in any order, changes nothing.
2. **A battle whose night game time has passed resolves on the day advance**, and
   the player is notified rather than discovering it. A player who never opens
   `/battles/[id]` still has the battle happen.
3. **A 2-1 renders as three stacked perspectives with a visible dissent**, and
   reads differently from a 3-0.
4. **Every decision line is reproducible** from the persisted decomposition —
   same battle, same words, on a fresh render and under a newer engine.
5. **Declining is reachable in two taps, carries no warning, and leaves nothing
   behind that implies failure.**
6. **The angle is chosen without the opponent's angle being knowable**, and
   scouting cannot be used to infer it.
7. **Preparation shows its cost in days as well as money.**
8. **No battle-reward screen exists**, and no surface announces a metric change.
9. **Everything works at phone width**, with the three perspectives stacked.

### Boundary — tested as strings, not reviewed by eye

The implementation must prove that **no player-facing battle surface** exposes any
of the following, in rendered output or in serialised props:

| Must not appear |
|---|
| performance fact quantities (any of the seven) |
| `artist_skills` values |
| `artist_psychology` values |
| judge decomposition numbers (totals, contributions, weights, inputs) |
| judge margins |
| strategy aptitude |
| internal crowd/cohort composition (shares, slugs, `qualities`, `attention`) |
| the rivalry number, or any relationship dimension as a figure |
| career metric deltas (Fame / Respect / Heat pressure) |
| simulator seed or engine version |
| internal battle coefficients |
| eligibility rule names, ranking scores, or director internals |

**World Control may expose all of these and must continue to.** The test asserts
the boundary, not the absence of the data.

## Sequence

1. **Resolve due battles on the day advance**, with a notification. Nothing below
   is reachable until a battle can finish.
2. **A player read model for battles** — the M7 pattern, `battle-view` beside the
   existing inspector query, projecting only what the boundary permits.
3. **The describers** — judge decision lines, round reading, scouting insights and
   aftermath lines. Pure, deterministic, beside the existing ones.
4. **The battle route**, in its two states: before the night (accept, scout,
   declare, prepare) and after it (the judges' decision).
5. **Home, Notifications, Calendar, Career, World** — each learning one new type.
6. **The decline path**, verified against its own criterion rather than assumed.
7. **The boundary test**, as a string assertion over rendered battle surfaces.
8. **The E2E walk**: challenged, scouted, declared, prepared, resolved on a day
   advance, read — and a second career that declines everything and is never
   nagged.

## The line to keep pinned

> **The player decides how to go into a room. They do not decide what happens in
> it, they are never shown the machinery that did, and they are never handed a
> receipt for it afterwards.**
