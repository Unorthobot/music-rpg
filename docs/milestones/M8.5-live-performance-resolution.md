# Milestone 8.5 — Live Performance Resolution

**Baseline:** tag `m8-final` (commit `630ef6d`). M0–M8 accepted and frozen. 326
unit/domain/integration tests and 30 E2E pass on a clean tree; typecheck and lint
are clean.

**Numbering.** This is `8.5` rather than `10` because it ships *before* M9. It
exists because M9's investigation could not be completed honestly without it, and
the number should say so rather than hide it behind a later index. Its migration
is `0014`; M9's unshipped `0014_m9_come_up` renumbers to `0015` when it resumes.

This is the headless brief. **No interface is built in this milestone.**

## The defect this milestone repairs

M7 already reported it, and M9 was stopped by it:

> `acceptOpportunity` writes a `PERFORMANCE` calendar item for a `SHOWCASE_SLOT`
> and **nothing in the game ever resolves it**.

The chain the game already promises, and where it stops:

```
director generates SHOWCASE_SLOT     ✓ works
player accepts                       ✓ works
PERFORMANCE calendar item written    ✓ works
game time reaches the night          ✓ happens
the night happens                    ✗ ██ nothing ██
calendar item completes              ✗
payout settles                       ✗
the scene learns about it            ✗
the opportunity resolves             ✗
career history records it            ✗
```

Three things are wrong today and each is worse than the last:

- **The game tells the player a night pays and it does not.** `getOfferView`
  returns `feeDirection: "EARNS"` for every showcase and surfaces `payoutMinor` —
  40 000 for Naledi's rooftop, 60 000 for Tumi's live room, 90 000 for Sizwe's
  Sunday. `TRANSACTION_CATEGORIES` is `STUDIO_COST · SESSION_REFUND ·
  STARTING_CAPITAL · OTHER`. There is no category through which a fee could
  arrive and no code path that would credit one.
- **The commitment never clears.** The calendar item stays `SCHEDULED` forever,
  which means it permanently fails `NIGHT_IS_FREE` for that window against every
  future offer. Accepting a night quietly makes the career slightly less bookable
  for the rest of its life.
- **A career cannot accumulate live evidence at all.** Not a small gap: the
  entire live limb of the causal chain is missing, and everything downstream of
  it — what a room does to an audience, what a promoter makes of somebody who
  turned up and delivered, what the scene saw — is unreachable.

## The question

> **What is the smallest thing that has to be true for a night to have actually
> happened?**

Not *what would a live-performance system eventually contain*. This milestone is
deliberately the smallest deterministic completion of a chain the game already
started, and the discipline that keeps it small is that **every input it consumes
already exists**.

## Archaeology

### What the world already holds

Everything a night needs to be resolvable is already recorded when the offer is
accepted:

| Fact | Where it already lives |
|---|---|
| Which night, in game time | `opportunities.payload.nightGameTime`, and `calendar_items.start_game_time` |
| Who booked it | `opportunities.source_entity_id` → the promoter character |
| The room | `preferences.promoter.capacity`, `nightName`, `termsLine` |
| Where | `opportunities.scene_id`, and the promoter's `sceneSlug` |
| Carrying it or opening it | `opportunities.payload.billing` — `HEADLINE` or `SUPPORT` |
| What it pays | `payload.payoutMinor`, already resolved to the correct one of `payoutMinor` / `supportPayoutMinor` |
| The commitment | `calendar_items` row, `type = PERFORMANCE`, `related_entity_id` → the opportunity |
| Who is playing | `careers.player_artist_id`, `artist_skills.performance` |
| Whether anything is moving | `release_performance.current_momentum` |
| How well the scene knows them | `sceneStanding()`, over M5's own cohort rows |

**Nothing in this list has to be invented.** The milestone's job is to consume it
on the day the clock reaches the night.

### The seam M8 built for exactly this

`advanceCareerDay` step 1.5 calls `resolveDueBattles`, and M8's own comment
names what it is:

> This is the seam a second scheduled event type joins — **beside this call, not
> inside it**. There is deliberately no registry: one event type does not
> demonstrate the need for one, and the ordering is the part worth preserving.

That instruction is followed literally. `resolveDuePerformances` is a sibling
call at step 1.5, not a generalised scheduler, and not a branch inside the battle
resolver.

**One simplification versus battles.** `guardAcceptedBattles` stops time crossing
an accepted battle whose angle has not been declared, because `resolveBattle`
genuinely cannot run without one. **A performance has no required pre-event
decision**, so it needs no guard and gets none. The night simply happens. A
player who accepts a night and then ignores the game entirely still played it,
which is both correct and the whole point of a scheduled world event.

### What does not exist

There is no live-performance schema of any kind. `battle_performances` is a
battle *round* — writing, flow, rebuttal, crowd work — and is unrelated.
There is no performance status vocabulary, no performance event type, and no
performance transaction category.

## What a performance is

> **A night is a bounded encounter between an artist and a room somebody else
> owns, on a date agreed in advance, whose consequences are limited by how many
> people were actually in it.**

Three clauses, each load-bearing:

- **A room somebody else owns.** The promoter set the terms, the bar and the fee.
  Nothing here is the player's to decide once the offer is accepted.
- **A date agreed in advance.** It happens because game time reached it. Never
  because a screen opened, and never because the player was ready.
- **Bounded by how many people were in it.** This is the rule that stops a live
  system becoming a second reception simulator, and it is stated as an invariant
  below rather than as an intention.

### Stored or derived

The same split M5–M8 already hold.

- **The night is stored.** A `performances` row, written once when it resolves,
  carrying what happened and the derivation that produced it. It is a world fact
  with participants, terms and consequences — the point at which `battles`
  stopped being a projection and became a system, reached by the same argument.
- **The consequences are stored where their owners already keep them.** Money in
  `transactions`, standing in `career_metric_pressure`, audience in
  `artist_audience`. No parallel ledger, no second pressure table, no new
  currency.
- **Nothing about a night is derived on read.** M6's rule, applied: a screen may
  reveal a night, and may never cause or recompute one.

### No universal quality score

The single most important shape decision, and M8's discipline carried forward
unchanged: **there is no `quality`, `score`, `rating` or `success` column, and no
column that could become one.**

A night records **three named observable facts**, each an integer, each bounded:

| Fact | Meaning | Hard bound |
|---|---|---|
| `attendance` | People who were in the room | **≤ the room's `capacity`** |
| `won_over` | Of those, how many left caring more than when they arrived | ≤ `attendance` |
| `word_left_the_room` | Of those, how many told somebody who was not there | ≤ `won_over` |

Beside them sits `derivation` — a named decomposition in the `RankingResult`
shape this codebase already uses everywhere, saying which recorded input
contributed what to each fact. That is the versioned half; the three facts are
the canonical half.

Nothing sums them. There is deliberately no fourth number that already knew the
answer, and a night that went badly is a night with a low `won_over` rather than
a night with a bad grade.

### What decides the three facts

Only inputs that already exist, and each is named in `derivation`:

- **`billing`** — carrying the night or opening it. Different rooms, different
  expectations, different numbers.
- **`capacity`** — the promoter's room. The ceiling on everything.
- **`sceneStanding()` in that scene** — how many people would turn up for this
  name, read through M7's own function and never recomputed.
- **`current_momentum`** on the career's best-moving release — whether anything
  is actually happening around this artist right now. Momentum decays, which is
  what makes a night booked off the back of a hot record different from one
  played six weeks after everybody stopped talking.
- **`artist_skills.performance`** — the one skill that has always meant this and
  has never had a consumer. A room is where it should matter.
- **A seed** — reproducible texture, in M5's idiom (`±` a small jitter derived
  from the seed), never noise. Same seed, same night.

**No new coefficient may be added to M5, M6, M7 or M8, and none of theirs may be
changed.** This milestone's constants live in one file of its own.

### SUPPORT and HEADLINE must mean different things

They already do, in the world's own terms, and the resolution must carry that
through rather than inventing a second distinction:

| | `SUPPORT` | `HEADLINE` |
|---|---|---|
| What the promoter said | *"We'll give you a chance."* | *"We trust you to carry the room."* |
| Fee | `supportPayoutMinor` (8 000 – 30 000) | `payoutMinor` (25 000 – 90 000) |
| The room | Some of it is there for somebody else | It is there for you |
| Expectation | Low. Doing well is a surprise. | High. Doing badly is a real fact. |

Concretely: a support slot reaches a **fraction** of the room, because most of
the people in it came for the headliner; a headline slot addresses the room. The
fraction is a named constant in this milestone's file, applied to `attendance`.
This is the same shape `SUPPORT_BILLING_FACTOR` already uses in ranking, and
deliberately not that constant — ranking prices *being told about* an offer and
this prices *what the night was*.

## Bounded consequences

The complete list. Nothing outside it is this milestone's.

### 1. The calendar closes

`calendar_items.status → COMPLETED`, and `calendar_item.completed` is emitted —
an event type declared since M2 that has never once been written for a
performance. The night stops being a commitment, which is what makes
`NIGHT_IS_FREE` true again for that window.

### 2. The offer reaches its ending

`opportunities.status → RESOLVED`, `resolved_at` set, `opportunity.resolved`
emitted. `RESOLVED` has meant *it happened* since M2 and no showcase has ever
reached it. M7's four endings finally have their fourth in use.

### 3. The fee settles

`TRANSACTION_CATEGORIES` gains **`PERFORMANCE_FEE`**, and the payout is credited
through `applyMoneyMovement` — the existing ledger, the existing running balance,
one transaction, idempotency-keyed. This is the first time money has moved *into*
a career in this game.

The amount is `payload.payoutMinor` **exactly as agreed when the offer was
accepted**. A night does not renegotiate itself: the terms were the promoter's
and they were recorded. Nothing scales the fee by how the night went, because
nobody in this world has ever been paid on results and inventing that would be
an economy rather than a repair.

### 4. Standing moves, proportionately and traceably

Fame, Respect and Heat move through `career_metric_pressure` — the existing
fractional accrual with its integer floor and `CAREER_METRIC_CEILING` — in
M8's idiom: named contributions, with the facts that caused them, recorded on the
performance row.

The proportionality rule is an invariant, not a preference:

> **A night's standing movement is bounded by `attendance`, never by `capacity`
> and never by anything else.** Eighty people in a basement move a career less
> than three hundred in Soweto, and a headline slot played to a half-empty room
> moves it like a half-empty room.

Heat in particular is what a night should produce — it is velocity, it decays,
and playing to a live room is exactly the kind of thing that should spike it and
then fade. Fame moves least: one night is not a broadcast.

### 5. A live audience effect, capacity-bounded — or nothing at all

**The rule that keeps this from becoming a second reception simulator:**

> **A night may never affect more people than were in the room.** Not more than
> the room's capacity, not more than `attendance`, not ever, under any
> composition of effects.

Within that bound, the implementation distributes `attendance` across M5's
cohorts by each cohort's own recorded `scene_affinity` for that scene — the same
concentration weighting `sceneStanding()` already uses — and writes, through a
single named function:

- `artist_audience.prior_exposure` — up by the attendees from that cohort,
  clamped by cohort `size`. These people have now encountered this artist.
- `artist_audience.affinity` — a small increment, weighted by `won_over`. Being
  in the room is a stronger encounter than hearing a track, and there are three
  orders of magnitude fewer people in it.
- `artist_audience.fans` — at most a bounded fraction of `won_over`. A room can
  make a handful of fans. It cannot make a thousand.

**What it must never write:** `release_performance` or `release_cohort_performance`
(a night is not a release and has no listeners), `career_audience.monthly_listeners`
or `.reach` (those are streaming-shaped and a room is not a stream), or anything
that would make a `reception_ticks` row.

**The escape hatch, and it is a real one.** If the implementation finds it cannot
write these rows without distorting M5 — if reception's replay guarantee, its
watermarks or its cohort projections cannot accommodate a second writer cleanly —
then **v1 ships with no audience effect at all**, and the finding is reported
rather than worked around. A night whose evidence is the fee, the standing
movement and the public fact is still a night that happened. Bending M5 to give
it an audience would cost more than it buys.

### 6. The scene learns about it

`performance.resolved`, `LOCAL_PUBLIC`, in the World feed beside releases and
battles, carrying the three facts, the room, the billing and the promoter. This
is the only `LOCAL_PUBLIC` event this milestone writes, and it is the one that
matters: **it is what makes a night a thing the scene saw.**

`performance.performed` (`PRIVATE`) may exist alongside it if the implementation
finds the two-step shape useful, exactly as `battle.performed` precedes
`battle.resolved`. It is optional; `performance.resolved` is not.

### 7. Career history

A `career_memories` row, in the shape everything else writes one, so
`career-story.ts` can narrate a night from persisted rows without being taught
anything new.

## What this milestone does not do

Each of these is a real thing a live system would eventually contain, and each is
excluded with a reason rather than by omission.

- **Promoter relationships.** A night is obviously a legitimate source of
  relationship history with the person whose room it was — and promoters have no
  `relationships` row today, because M6 derives relationships from creative
  sessions. Creating the first non-studio relationship source requires explicit
  M6 interaction semantics (which interaction kind, what it costs, what a bad
  night does), and that is M6's milestone rather than a generic delta smuggled in
  here. **The performance row keeps full promoter identity and context so a later
  milestone can consume it without re-deriving anything.**
- **Anything the room is not.** No touring, ticketing, venue economy, festivals,
  setlists, merch, live audio, animation, crowd simulation, managers, labels,
  contracts, or new reward currencies.
- **Renegotiation.** No fee scaling, no bonuses, no penalties, no missed nights
  costing money. The terms were agreed.
- **M9 progression logic.** See below — the separation is architectural.

## The M9 seam

**One-directional, through the event log, and the direction is not negotiable.**

This system emits `performance.resolved` as a canonical `LOCAL_PUBLIC` fact and
knows nothing else. It imports nothing from progression, references no evidence
family, contains no reference to `career_act`, and would behave identically if M9
never shipped. **A performance resolver that knew what a night was worth to a
phase would be two systems in one file.**

M9 later adds one string to a closed allow-list it already has:

```ts
SCENE_WITNESSED_EVENT_TYPES = [
  "release.published",
  "battle.resolved",
  "performance.resolved",   // ← the entire coupling
]
```

That single line is why this milestone exists. M9's audit established that
`THINGS_THE_SCENE_SAW` requires **more than one kind** of world-witnessed fact,
and that `battle.resolved` was its only second satisfier — which meant public
recognition was reachable only by fighting somebody. A resolved night is the
honest second kind, and it restores the career that plays rooms rather than
battles.

**Nothing in this milestone may be justified by that.** If a design choice here
is defensible only because it helps M9 qualify a career, it is the wrong choice.
A show should become a real thing that happened, and M9's opinion about it comes
later or not at all.

## Determinism, idempotency, replay

- **Resolution is pure, given the facts.** The night's three facts come from a
  deterministic function of recorded inputs and a seed. No clock, no `Date.now()`,
  no network. `simulator_version` and `seed` are stored on the row, so a formula
  change never rewrites a night that already happened.
- **Exactly once.** Keyed `performance:{id}:resolved`. Repeated day advances must
  not pay twice, emit twice, move standing twice, or touch the audience twice.
  This is the assertion most likely to be got subtly wrong, because four
  different systems are being written to in one transaction.
- **One transaction.** The performance row, the calendar completion, the
  opportunity resolution, the ledger entry, the pressure accrual, the audience
  writes and the events all commit together or none of them do.
- **A failure must not undo the day.** The same tolerance `resolveDueBattles` and
  the director already get: reception has happened and the clock has moved, so a
  night that cannot resolve is reported and retried on the next advance.
- **Replay-exact.** Same seed, same sequence of advances: the same night, the
  same three facts, the same fee, the same events.
- **Only due nights.** `status = SCHEDULED AND scheduled_game_time <= career.currentGameDate`,
  ordered ascending — `resolveDueBattles`' query shape, deliberately.

## The headless golden proof

| # | Proof | Assertion |
|---|---|---|
| 1 | **Time causes it** | Accept a night, advance past it, never open a screen → it resolved. Open every screen ten times without advancing → nothing happened. |
| 2 | **Acceptance is not evidence** | A career that accepted a night it has not reached has no `performances` row, no `performance.resolved`, no fee and no standing movement. **The assertion M9 depends on.** |
| 3 | **Billing means something** | The same room, the same career, `HEADLINE` vs `SUPPORT`: different `attendance`, different fee, traceable to `payoutMinor` vs `supportPayoutMinor` and to the named support factor. |
| 4 | **No quality score exists** | Three named facts and a derivation. Asserted structurally — no column, no field, no payload key that totals them. |
| 5 | **The calendar closes** | `status = COMPLETED`, `calendar_item.completed` emitted once. |
| 6 | **The night frees up** | After resolution the window stops failing `NIGHT_IS_FREE`, proved by a later offer for the same window becoming eligible. |
| 7 | **The offer ends properly** | `opportunities.status = RESOLVED`, `opportunity.resolved` emitted. |
| 8 | **Money moves** | `careers.money_balance` up by exactly `payoutMinor`; one `transactions` row, `CREDIT`, `PERFORMANCE_FEE`, `balance_after_minor` reconciling with the career. |
| 9 | **Standing is bounded and traceable** | Fame/Respect/Heat movement decomposed into named contributions; a 80-capacity basement moves a career measurably less than a 300-capacity Sunday, attributable to `attendance`. |
| 10 | **Capacity bounds everything** | Across every cohort, the total people affected by a night ≤ the room's capacity. Asserted as an invariant over the audience diff, not as a spot check. |
| 11 | **A night is not a release** | No `release_performance`, `release_cohort_performance` or `reception_ticks` row is created or altered by a performance. |
| 12 | **`performance.resolved` exactly once** | `LOCAL_PUBLIC`, under any number of repeated advances. |
| 13 | **Idempotent in full** | Ten further advances after resolution: no second fee, no second event, no second pressure accrual, no second audience movement. |
| 14 | **Legacy remains 0** | `careers.legacy` and `artists.legacy` are `0` for every career in the suite. |
| 15 | **Replay-exact** | Two worlds, same seed, same advances: identical rows and identical events. |
| 16 | **No M5–M8 regression** | The full existing suite, green, with no assertion changed to accommodate this milestone. |

## Falsifiable conditions

The design is **wrong** — not badly tuned — if any of these is true:

1. A night resolves because somebody opened a screen.
2. An accepted night counts as a night that happened.
3. A night affects more people than the room holds.
4. A night writes a `reception_ticks` row, or is otherwise simulated as a release.
5. The fee varies by how the night went.
6. A repeated advance pays twice, or emits `performance.resolved` twice.
7. `SUPPORT` and `HEADLINE` produce identical facts.
8. A single number decides whether the night was good.
9. Any M5–M8 coefficient changed.
10. The performance resolver contains any reference to career acts, evidence
    families or progression.
11. Standing moves by more than a room's worth, or moves without a recorded
    decomposition.
12. A resolved night still blocks the calendar.

## World Control

The inspector must reconstruct the chain without inference:

```
the offer, with the promoter's terms as recorded
  → the acceptance, and the commitment it created
  → the night the clock reached
  → attendance, won over, word that left the room — each with its derivation
  → the fee, and the ledger row it became
  → Fame / Respect / Heat movement, decomposed
  → who in the audience was touched, cohort by cohort, within capacity
  → performance.resolved, as the scene saw it
```

And for a night that has **not** happened yet: that it is scheduled, for when,
and that nothing has been paid or moved — because *"this has not happened"* is
the answer M9 will depend on being able to trust.

## Implementation sequence

Locked, and each step is the precondition for the next.

1. **Vocabulary** — `PERFORMANCE_FEE`, the performance statuses, the three fact
   names and the event types, as closed lists in `shared`, named before anything
   produces them.
2. **The pure resolver** in `simulation/performances/` — facts in, three facts
   out, with a derivation. No database, no clock. Testable against hand-built
   inputs before a world exists around it.
3. **Schema** — `0014`, the `performances` table, and the calendar/opportunity
   states it drives.
4. **Fact assembly and the transaction** in `domain` — reading the offer, the
   promoter, the scene, the momentum and the skill; writing everything in one
   transaction.
5. **`resolveDuePerformances`** at step 1.5, **beside** `resolveDueBattles`.
6. **The ledger** — the fee, through `applyMoneyMovement`.
7. **Standing** — bounded pressure with its decomposition.
8. **The audience effect**, capacity-bounded — **or the report that it cannot be
   done cleanly**, which is an acceptable outcome of this step.
9. **`performance.resolved`**, `LOCAL_PUBLIC`, exactly once.
10. **The golden proof**, all sixteen assertions.
11. **World Control causality**, for a night that happened and one that has not.
12. **Stop before any interface.** The player experience is a later milestone, as
    it was for M7 and M8.

## Acceptance criteria

- An accepted showcase resolves on the advance that reaches its night, and never
  before, and never on a render.
- A career that accepted a night it has not reached has no performance evidence
  of any kind.
- `SUPPORT` and `HEADLINE` nights at the same room produce materially different
  recorded facts and different fees.
- No performance record contains a total, score or grade.
- The calendar item completes; the opportunity reaches `RESOLVED`; the window
  becomes bookable again.
- The fee credits exactly once, through `transactions`, as `PERFORMANCE_FEE`,
  with the career balance reconciling.
- Fame/Respect/Heat movement is decomposed, traceable and bounded by attendance.
- **Total audience affected by a night never exceeds the room's capacity**, or
  no audience effect ships and the reason is documented.
- `performance.resolved` exists exactly once per performance under any number of
  repeated advances, and is `LOCAL_PUBLIC`.
- `careers.legacy` and `artists.legacy` are `0` throughout.
- Replay is exact; the full M0–M8 suite is green with no assertion changed.
- Nothing in this milestone references M9.

## What would justify `m8.5-final`

The headless proof above, complete — and one thing more, which is the only real
test of the milestone:

**A player who accepts a night, forgets about it, and comes back a week later
should find that it happened, that they were paid, and that the scene knows.**

## The line to keep pinned

> **A show should become a real thing that happened before anything is allowed to
> treat it as evidence.**
